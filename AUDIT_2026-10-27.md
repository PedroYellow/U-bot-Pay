## L-2 — duplicated security headers

### Root cause

nginx's `add_header` inheritance rule: **a location block that declares any
`add_header` directive discards every inherited one.** The vhost had a
server-level set of six security headers, and then re-declared the same
headers inside five exact-match asset locations (`/ubot.css`, `/i18n.js`,
`/manifest.json`, `/sw.js`) and inside the `location /` SPA catch-all. Each
of those locations therefore emitted a *second* copy of each header, and the
browser enforced the first one it saw.

There were also two separate server-level sets: the rich one (with the
ElevenLabs endpoints the microphone needs) and the older "Security headers
(audit #6)" set with a looser CSP and `Referrer-Policy: no-referrer`.

### Fix

1. Deleted the duplicate server-level "audit #6" set. The richer set is now
   the single canonical one.
2. Removed the per-location security-header copies. The locations now inherit
   the server-level set.
3. Replaced `add_header Cache-Control "…"` with the `expires` directive in
   those locations. `expires` is not an `add_header`, so it does not break
   inheritance — this is what lets the locations keep their cache behaviour
   *and* inherit the security headers. `no-cache` → `expires -1`,
   `public, max-age=86400` → `expires 1d`.

> This is the detail the three earlier failed attempts missed. The asset
> locations needed a cache directive, `add_header Cache-Control` was the only
> one they had, and it was exactly what re-triggered the inheritance drop.
> Stripping the `add_header` line without replacing it with `expires` would
> have silently changed the cache policy.

### Verified

Every path returns each security header **exactly once**:

```
/              1× CSP, 1× HSTS, 1× nosniff, 1× DENY, 1× Referrer-Policy, 1× Permissions-Policy
/index.html    (same)
/ubot.css      (same)
/i18n.js       (same)
/manifest.json (same)
/sw.js         (same)
/favicon-32x32.png
/pitch/
/agent.html
```

`agent.ubotpay.com` is a **separate server block** with its own (smaller)
header set — that is correct, it is a different host with a different CSP.
The test asserts *at most one* declaration per header per server block, not
one across the whole file.

## L-3-static — backup files served from the webroot

### What was actually there

Eight files, not six — two more had appeared since round 3:

```
index.html.bak-021648      agent.html.bak-021648
index.html.bak-050202      analytics.html.bak-021648
index.html.before-fix3     sw.js.bak-021648
index.html.pre-fix-agent   sw.js.bak-050226
```

All eight were served with HTTP 200 and `Content-Type: application/octet-stream`
with their full bytes. `index.html.bak-021648` contains the unpatched bridge
error handler `status.innerHTML = "❌ Bridge failed: " + (b.error || …)` —
a second-order XSS (the live `index.html` already escapes it with `esc()`).

### Fix

1. **Captured off-webroot first.** All eight copied to
   `/root/audit/20261027-baks-captured/` with md5s recorded, before deletion.
   The path is outside `/var/www/`, so it is not world-accessible.
2. **Removed from the webroot.**
3. **Added an nginx deny rule** so a future deploy cannot re-expose them:

```nginx
location ~* \.(bak|before|after|pre|post|orig|tmp|swp|save|old|backup)(\.|[-_]|$) {
    return 404;
}
location ~* (before-fix|pre-fix|post-fix|fix)[-_a-z0-9]*\.(html|js|css|json|txt)$ {
    return 404;
}
```

The rules are placed **before** the `location /` SPA catch-all. They are
regex locations, so nginx evaluates them after the longest prefix match but
before the `location /` fallback — they win over the SPA rewrite.

> Placement matters and cost one iteration: on the first attempt the deny
> rule was inserted after the catch-all and had no effect, because the
> `location /` prefix match was being taken first.

### Verified

```
index.html.bak-021648     -> 404
index.html.bak-050202     -> 404
agent.html.bak-021648     -> 404
analytics.html.bak-021648 -> 404
sw.js.bak-021648          -> 404
sw.js.bak-050226          -> 404
index.html.before-fix3    -> 404
index.html.pre-fix-agent  -> 404
test.bak / file.tmp / index.html.orig / x.swp / index.html.old -> 404
```

Real assets still serve: `index.html`, `ubot.css`, `i18n.js`, `sw.js`,
`manifest.json`, `agent.html`, `analytics.html`, `security.txt`,
`favicon-32x32.png` → all 200.

## S-3 — treasury address hardcoded in the footer

The treasury address was a literal string in `web/index.html`, so it was
baked into every cached copy of the site and could not be rotated without a
full redeploy. The address is on-chain anyway, so this was never a secret
leak — but it was not rotatable and it was not opt-out.

### Fix

**New public endpoint** (`api.py`):

```
GET /treasury
-> {"ok":true,"address":"0x673678…","explorer":"https://snowtrace.io/address/0x673678…","visible":true}
```

`visible` is driven by `UBOT_SHOW_TREASURY_ON_HOMEPAGE` (default `true`).
Set it to `false` and the footer link hides itself; set the address in
`UBOT_WALLET_ADDRESS` and the link follows it, with no redeploy.

**Footer** (`web/index.html`): the anchor is now
`<a id="treasuryLink" … style="display:none">` and a small loader fetches
`/treasury` at runtime, sets the `href`, and reveals the link. If the fetch
fails or `visible` is false, the link stays hidden.

### Verified

- The literal address no longer appears in the live HTML: `grep -c` → **0**.
- `/treasury` returns 200 with the address, explorer link and `visible` flag.
- CORS works for the `ubotpay.com` origin (GET → `Access-Control-Allow-Origin:
  https://ubotpay.com`; OPTIONS → 204 with the same origin and
  `GET, POST, OPTIONS`).
- An nginx route was added for `/treasury` — without it the SPA catch-all
  answered with `index.html` and the footer fetched HTML instead of JSON.

## F-8 — `/auth/wallet/nonce` accepted any chain_id

`chain_id` was taken verbatim, so `chain_id: 99` returned 200 and a nonce
row. The user would then sign a message naming a chain that does not exist,
and no supported chain could ever redeem it — a dead-end signature, and a
DoS surface for a user tricked into signing.

### Fix

`api.py` now resolves the chain against the registry before minting:

```python
try:
    chain.get_chain(req.chain_id)
except ValueError:
    raise HTTPException(400, f"unsupported chain_id={req.chain_id}")
```

### Verified

```
chain_id=99    -> 400 {"detail":"unsupported chain_id=99"}
chain_id=43114 -> 200   (Avalanche)
chain_id=146   -> 200   (Sonic)
```

## L-3b — the treasury balance was public (found and fixed during this round)

**This is the most important finding in this document, and it was not in any
audit round.**

### What happened

The round-1 audit (L-3) found that `/balance/{addr}` returned balances for
any address without authentication. The fix — an allow-list, so that only
the demo and burn addresses are readable anonymously — was applied **directly
to the deployed file** on the VPS on 21 Oct.

It was never applied to the repository. `git log -S` on `api.py` shows the
commit `c8a5cca` "feat(api): allow-list anonymous /balance/{addr} reads
(audit L-3)" **changed only the audit document, not a single line of code**:

```
$ git show c8a5cca --stat
 AUDIT_2026-10-21c_live.md | 49 ++++++++++++++++++++++++++++++++++++++++
 1 file changed, 49 insertions(+)
```

When the repository was synced over the deployment (which is how every
deploy works), the guard was overwritten and the endpoint went back to
serving any address. The audit document still said the fix was live. The
two disagreed for six days, and nobody noticed because the round-2 and
round-3 audits re-verified the *live* endpoint and recorded it as
**"treasury and revenue both return 401"** — which was true on 21 Oct, and
stopped being true later.

### What was actually exposed

Verified live immediately before the fix:

```
$ curl https://api.ubotpay.com/balance/0x673678B1870Ae7ef598A5982D25ffdee68d85669
{"address":"0x673678B1870Ae7ef598A5982D25ffdee68d85669","chain":"Avalanche C-Chain",
 "chain_id":43114,"native":"AVAX","native_balance":0.29249245993280193,"usdc":18.32}
```

The treasury's live balance — 18.32 USDC and 0.29 AVAX — readable by
anyone, without authentication, for an unknown period. The revenue wallet
(`0xbE440bf2…`) was equally readable.

### Fix

The guard is now **in the repository**, in `api.py`, with the same
semantics the audit round originally described:

```python
def _anon_balance_allowlist() -> set[str]:
    raw = os.environ.get(
        "UBOT_BALANCE_ANON_ALLOWLIST",
        "0x000000000000000000000000000000000000dEaD,"
        "0x713261F2151a759d9D935e6De2DB1d63A98176f6",
    )
    return {a.strip().lower() for a in raw.split(",") if a.strip()}
```

applied inside `balance_by_address`:

```python
if address.lower() not in _anon_balance_allowlist():
    auth(x_api_key)
```

### Verified

```
/balance/<treasury>                      -> 401  (anonymous)
/balance/<revenue wallet>                -> 401  (anonymous)
/balance/<demo address>                  -> 200  (allow-listed)
/balance/<burn address>                  -> 200  (allow-listed)
/balance/<treasury> with X-API-Key       -> 200  (key-gated)
```

### The process failure behind it

Two things went wrong, and both are worth fixing:

1. **A fix that lives only on a deployed server is not a fix.** It will be
   overwritten by the next deploy, and the audit document will keep
   claiming it is there. Every fix from now on goes into the repository
   first.
2. **The audit rounds re-verified the endpoint but not the claim.** Round 2
   and round 3 both recorded "treasury returns 401" as a *verified
   positive*. That was a true statement about the server at that moment —
   but nothing checked that the repository and the server agreed.

`test_audit_round3_fixes.py` now closes both gaps: it reads `api.py` from
the source tree and asserts the guard is present, and it checks the live
endpoint. The source assertion is the one that would have caught this.

## Test results

**New suite: `test_audit_round3_fixes.py` — 40/40 passed.**

It asserts the vhost file (duplicated headers, deny rule, `expires`
conversion), the webroot contents, the live backup URLs returning 404, the
treasury endpoint and the absence of the hardcoded address, the nonce
chain validation both in-process and over HTTP, the balance allow-list
**both in the source and on the live endpoint**, and that the public API
surface still answers.

**Existing suite: 40/40 suites pass, `EXIT=0`** after one fix to
`run_tests.sh`.

The runner was invoking the *system* `python3` instead of the project
venv's interpreter. The venv is where `fastapi`, `httpx`, `web3` and
`eth_account` live, so five suites died at import with
`ModuleNotFoundError` and were reported as FAIL — an environment artefact,
not a product regression. Re-run with the venv python, all five pass
(35/35, 42/42, 30/30, 30/30, 12/12). The runner now prefers
`/opt/ubotpay/venv/bin/python` and falls back to `python3` where no venv
exists.

## Carried forward

- The nginx vhost is deployed separately from the app and had drifted from
  the repo copy (the live file was 226 lines against the repo's 221). It is
  now synced back into `deploy/nginx.conf`, but there is no automation keeping
  them in step — worth a deploy script that pushes the vhost from the repo.
- ~~The webroot accumulates `.bak-*` files on every deploy.~~ **Fixed.**
  `deploy_web.sh` now archives any stray backup file to
  `/root/audit/web-archive/` (timestamped) before removing it, and the
  verification step fails the deploy if any backup file survives in the
  webroot. The nginx deny rule remains the second line of defence.
- `agent.ubotpay.com` has its own smaller header set and no
  `Permissions-Policy`. Not a finding, but it was never reviewed on its own.
- **The deployment model is the real root cause behind L-3b.** The
  repository is copied over the running app, so any fix applied only on the
  server is lost on the next deploy — and the audit documents keep claiming
  it is there. The rule now is: *the fix goes into the repository first, and
  the test reads the source.* Two separate failures followed from this
  (L-2, L-3b), so it is worth making the deploy script itself assert that
  the running service matches the repository, not just copy it.
