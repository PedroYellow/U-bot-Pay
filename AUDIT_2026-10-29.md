# AUDIT 2026-10-29 — the angle that was missing

## The pattern in every bug found in this round

Three real bugs in two days, and every one of them shared the same
shape: **the feature worked perfectly from inside the server and was
broken for anyone coming from the internet.**

- `/bridge/quote` answered **400** to every public caller, and 200
  from localhost. A duplicated `proxy_set_header Host` made nginx
  send two Host headers; uvicorn rejects those with "Invalid HTTP
  request received."
- `/bridge/chains` answered **500** on the Starknet deployment, and
  200 on the other two. `StarknetEngine` inherits from nothing, so
  it did not get `ChainEngine.explorer()`.
- The drift check could not see either one. It compares the
  repository against the deployment — **both of which are inside the
  server**. A vhost can be byte-identical to the repository and still
  be broken.

The test suite could not see them either. It runs on the VPS.

So the checks that were supposed to catch these were checking the
wrong vantage point. Everything was green and the features were
broken.

## What was fixed

### The duplicated Host header

`deploy/nginx-vhosts/*.conf` — the `/turn` and `/bridge/quote` blocks
had two `proxy_set_header Host $host;` lines. nginx sends both, and
uvicorn answers 400.

Affected `ubotpay`, `usonicpay` and `ustartkpay`. `usolpay` and
`utronpay` were clean.

`deploy/fix_duplicate_host_header.py` removes the second one and
keeps the first. It had to be careful: the first version removed the
wrong line when `proxy_set_header Host` shared a line with
`proxy_pass`.

### The Starknet engine's missing interface

`class StarknetEngine:` inherits from nothing. Six of the methods the
app calls were missing:

| method | why |
|---|---|
| `explorer` | the one that broke `/bridge/chains` |
| `send` | submit then confirm |
| `account` | the account object |
| `sign_authorization` | EIP-3009, EVM-only |
| `verify_authorization` | EIP-3009, EVM-only |
| `settle_authorization` | EIP-3009, EVM-only |

The x402 ones raise `NotSupported` with the reason the base class
uses: *transferWithAuthorization is an EVM-only primitive, and
Starknet is not EVM.* Saying that plainly beats an `AttributeError`.

`NotSupported` is defined locally in the engine, because the engine
is a standalone file — it is copied into `chains/` as `starknet.py`,
so it cannot do a relative import of the base class.

## The checks that would have caught them

### `deploy/check_nginx_host_headers.py` — static

Parses each `location` block and counts the `Host` headers. Two is
the bug.

It is static on purpose. The runtime symptom is a 400 that looks
like a malformed request, and it only appears from outside — so a
test that had to make the request from outside to notice would need
the internet and would be flaky.

One thing it deliberately does **not** flag: a block with a
`proxy_pass` and no `Host` header. nginx passes the original Host
through by default, and several locations in `usolpay` and `utronpay`
rely on that. The first version of the check required a Host
everywhere and produced fourteen false positives — which is how the
difference between *missing* and *duplicated* got pinned down.

- 5/5 on the repository's vhosts
- 9/9 on the live vhosts, including four the check had never looked
  at: `default`, `greenrail`, `swat`, `usonicpay-acme`

### `deploy/ustartkpay/check_starknet_interface.py` — static

Compares the Starknet engine's public surface with the EVM engine's
**effective** surface — the base class plus its own, since the EVM
engine inherits. It reports "nothing missing" now, and the Starknet
engine turns out to have four names the EVM one does not: `client`,
`name`, `token_name`, `token_symbol`.

### `deploy/check_public_endpoints.py` — from outside

27 endpoints across the three API domains, over the public internet,
from a machine that is not the server.

Two things it had to get right:

- **The destination address has to match the destination chain's
  format.** The source stays EVM in every case — the user signs an
  `eth_sendTransaction` payload on it — but the destination may be a
  non-EVM chain, where `to_address` is a base58 mint. With an EVM
  address on the Sonic deployment the service answers 400, which is
  the service validating the request, not a broken endpoint.
- **A 502 is not a broken endpoint.** LI.FI has no quote for every
  pair at every size, and the upstream answer is transient. It is
  reported as WARN, separately from the failures.

The body is not truncated. It was truncated to 400 bytes at first,
and the quote's JSON is longer than that — so the check read a
partial document, failed to parse it, and reported a working quote as
a failure.

### Both wired into `test_deploy_drift.py`

- **D4** — the nginx vhosts have one Host header per location
- **D5** — the Starknet engine implements the whole engine interface

D5 runs over SSH, reading the script from the deployment's copy: the
repository is on one machine and the deployment on the other, so a
path that exists here does not exist there. A check that reads the
deployment has to run where the deployment is.

## Not a bug, but worth knowing

`/push/vapid-key` returns `public_key: ""` on the Sonic and Starknet
deployments. Only `ubotpay` has VAPID keys.

The front-end handles it — `if (!vapidKey) return;` — so the push
subscription is simply skipped and nothing breaks. It is a graceful
degradation, not a fault.

If push is wanted on those domains, each needs its own VAPID key
pair. The keys are secret and are not shared between domains.
