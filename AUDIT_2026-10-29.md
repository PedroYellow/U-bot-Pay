# AUDIT 2026-10-29 — the angle that was missing

## The pattern in every bug found in this round

Three real bugs in two days, and every one of them shared the same
shape: **the feature worked perfectly from inside the server and was
broken for anyone coming from the internet.**

- `/bridge/quote` answered **400** to every public caller, and 200
  from localhost. A duplicated `proxy_set_header Host` made nginx
  send two Host headers; uvicorn rejects those with "Invalid HTTP
  request received."
- `/bridge/chains` answered **500** on the Starknet deployment, and
  200 on the other two. `StarknetEngine` inherits from nothing, so
  it did not get `ChainEngine.explorer()`.
- The drift check could not see either one. It compares the
  repository against the deployment — **both of which are inside the
  server**. A vhost can be byte-identical to the repository and still
  be broken.

The test suite could not see them either. It runs on the VPS.

So the checks that were supposed to catch these were checking the
wrong vantage point. Everything was green and the features were
broken.

## What was fixed

### The duplicated Host header

`deploy/nginx-vhosts/*.conf` — the `/turn` and `/bridge/quote` blocks
had two `proxy_set_header Host $host;` lines. nginx sends both, and
uvicorn answers 400.

Affected `ubotpay`, `usonicpay` and `ustartkpay`. `usolpay` and
`utronpay` were clean.

`deploy/fix_duplicate_host_header.py` removes the second one and
keeps the first. It had to be careful: the first version removed the
wrong line when `proxy_set_header Host` shared a line with
`proxy_pass`.

### The Starknet engine's missing interface

`class StarknetEngine:` inherits from nothing. Six of the methods the
app calls were missing:

| method | why |
|---|---|
| `explorer` | the one that broke `/bridge/chains` |
| `send` | submit then confirm |
| `account` | the account object |
| `sign_authorization` | EIP-3009, EVM-only |
| `verify_authorization` | EIP-3009, EVM-only |
| `settle_authorization` | EIP-3009, EVM-only |

The x402 ones raise `NotSupported` with the reason the base class
uses: *transferWithAuthorization is an EVM-only primitive, and
Starknet is not EVM.* Saying that plainly beats an `AttributeError`.

`NotSupported` is defined locally in the engine, because the engine
is a standalone file — it is copied into `chains/` as `starknet.py`,
so it cannot do a relative import of the base class.

## The checks that would have caught them

### `deploy/check_nginx_host_headers.py` — static

Parses each `location` block and counts the `Host` headers. Two is
the bug.

It is static on purpose. The runtime symptom is a 400 that looks
like a malformed request, and it only appears from outside — so a
test that had to make the request from outside to notice would need
the internet and would be flaky.

One thing it deliberately does **not** flag: a block with a
`proxy_pass` and no `Host` header. nginx passes the original Host
through by default, and several locations in `usolpay` and `utronpay`
rely on that. The first version of the check required a Host
everywhere and produced fourteen false positives — which is how the
difference between *missing* and *duplicated* got pinned down.

- 5/5 on the repository's vhosts
- 9/9 on the live vhosts, including four the check had never looked
  at: `default`, `greenrail`, `swat`, `usonicpay-acme`

### `deploy/ustartkpay/check_starknet_interface.py` — static

Compares the Starknet engine's public surface with the EVM engine's
**effective** surface — the base class plus its own, since the EVM
engine inherits. It reports "nothing missing" now, and the Starknet
engine turns out to have four names the EVM one does not: `client`,
`name`, `token_name`, `token_symbol`.

### `deploy/check_public_endpoints.py` — from outside

27 endpoints across the three API domains, over the public internet,
from a machine that is not the server.

Two things it had to get right:

- **The destination address has to match the destination chain's
  format.** The source stays EVM in every case — the user signs an
  `eth_sendTransaction` payload on it — but the destination may be a
  non-EVM chain, where `to_address` is a base58 mint. With an EVM
  address on the Sonic deployment the service answers 400, which is
  the service validating the request, not a broken endpoint.
- **A 502 is not a broken endpoint.** LI.FI has no quote for every
  pair at every size, and the upstream answer is transient. It is
  reported as WARN, separately from the failures.

The body is not truncated. It was truncated to 400 bytes at first,
and the quote's JSON is longer than that — so the check read a
partial document, failed to parse it, and reported a working quote as
a failure.

### Both wired into `test_deploy_drift.py`

- **D4** — the nginx vhosts have one Host header per location
- **D5** — the Starknet engine implements the whole engine interface

D5 runs over SSH, reading the script from the deployment's copy: the
repository is on one machine and the deployment on the other, so a
path that exists here does not exist there. A check that reads the
deployment has to run where the deployment is.

## Not a bug, but worth knowing

`/push/vapid-key` returns `public_key: ""` on the Sonic and Starknet
deployments. Only `ubotpay` has VAPID keys.

The front-end handles it — `if (!vapidKey) return;` — so the push
subscription is simply skipped and nothing breaks. It is a graceful
degradation, not a fault.

If push is wanted on those domains, each needs its own VAPID key
pair. The keys are secret and are not shared between domains.

# Round 2 — the same day, later

The first round above found the bugs that the checks could see. This
one found the ones they COULDN'T, because each of them was a case of
the same mistake in a new place.

## `/treasury` answered 200 with the site's HTML

The endpoint was added in audit round 3 (S-3), to make the treasury
address rotatable instead of baked into the static HTML. It went to
three deployments and not to the other two:

    ubotpay      SI
    usonicpay    SI
    ustartkpay   SI
    usolpay      NO
    utronpay     NO

And the nginx vhosts had no `location = /treasury` either, so on
those two the request fell through to the SPA catch-all and the API
host answered 200 with the site's HTML. A 200 that is not the
endpoint.

`check_public_endpoints.py` did not catch it, for two reasons, and
both are worth writing down:

  - it only looked at the STATUS CODE. A JSON API answering
    text/html is a broken route that reads as healthy.
  - it only covered the three domains it was written for. The two
    with the bug were the two it did not look at.

So the check now reads the Content-Type and covers all five API
domains. 45 endpoints, 0 failures.

The endpoint itself could not be a copy of the source's, because the
deployments do not agree on how to expose the treasury:

    the facade maps WALLET_ADDRESS to the engine's _treasury_address,
    which on Solana is a METHOD - so reading the attribute gives the
    bound method, not the address

    the Tron engine names it treasury_address() instead

    and the env vars are all different: USOL_WALLET_ADDRESS,
    Utron_WALLET_ADDRESS, UBOT_WALLET_ADDRESS - and EXPLORER is not
    defined in the Solana .env at all.

So it resolves the address through the engine - the public name
first, then the private one, calling it if it is callable - and reads
the explorer from the facade. An address is a string; a bound method
is not.

## `/balance` answered 500 on Tron

The balance guard watch cron had been reporting this and nobody had
looked:

    utronpay: demo=500(want 200 or 400)

Its own comment says what a 500 means:

    a 401 would mean the guard rejected it, and a 500 would mean the
    guard is broken.

The guard was right and the endpoint was broken. Two causes, both
from api.py being carried over from U-bot Pay with Avalanche's chain
id.

The default was 0, and 0 is not in the Tron profile. `chain.get_chain`
raises `NotSupported` for that - which is NOT a `ValueError`, so the
endpoint's `except ValueError` did not catch it:

    chains.engine.NotSupported: chain 0 is not in this profile
    500 Internal Server Error

And 0 was wrong too. TRON's chain id is 728126428 - the profile says
so, `chain.CHAIN_ID` reports it, and the registry indexes its
engines by it. The 0 came from LI.FI's era, and it had already been
mistaken once: one place had been changed from 43114 to 0 for this
exact reason.

Every default now comes from the profile, read at deploy time rather
than hardcoded - hardcoding is how the Avalanche value got here.
And `NotSupported` is caught as well as `ValueError`, so a chain
that is not in the profile is a 400.

## The Starknet deploy failed every single time

The deploy reported EXIT=1 and then EXIT=120, and stopped right
after `pip show starknet-py`. The venv underneath was perfect:

    rc     : 0
    stdout : 'No broken requirements found.\n'

The check was:

    out = subprocess.run([... "pip", "check"], ...).stdout.strip()
    if out:
        sys.exit(1)

`pip check` PRINTS on success. So `out` is never empty - not even
when everything is fine - and the success path was taken as a
conflict. With `|| exit 1`, the deploy died at the last step, every
time, with a clean venv underneath.

The exit code is the signal.

And the repository's copy of the script had ALREADY been fixed. The
copy on the server was the old one, and the drift check did not look
at the deploy scripts. So D1b now compares them - the deploy script,
the requirements, the EVM stub and the engine.

A script that is not the repository's is a script that will do
something the repository does not say it does.

## The Solana treasury has no USDC

Found by running the whitelabel suites again:

    the SOL:  0.099626    <- gas, and that is all there is
    the USDC: 0           <- it does not even have the ATA

On Solana the fee is paid in SOL and the token is transferred
separately, so a treasury can hold enough SOL to sign a transaction
and still have nothing to send. The chain says it:

    Program log: Error: insufficient funds

It showed up as two failures that looked like software faults and
were not. The concurrent-confirm test asserted "settled", but
"settled" means the payment was SENT, which needs a funded treasury
- the thing it guards is DOUBLE SETTLEMENT, and that held. The
transaction simulation expected the chain to accept a USDC transfer
and got "insufficient funds" - the chain being right.

Both now say what they can actually prove, and the settle/fail split
is printed as a note.

## The runner needs bash

`set -o pipefail` is a bash option. Run under dash - which is what
`sh` is on Debian - the runner dies with:

    set: Illegal option -o pipefail

which says nothing about the real problem. The runner has a bash
shebang, so `./run_tests.sh` works; only `sh run_tests.sh` breaks.
It says so plainly now, and the check comes BEFORE the set, or dash
would die on the option before reaching the message.

## A timeout that was too TIGHT

The journal test read the service's journal since the last restart -
76666 lines, 17 seconds to read them - with a 20-second timeout.
Under a load of 61 that is not enough, so it died with
TimeoutExpired and the assertion reported:

    FAIL  the Telegram bot token is not written to the journal

Which reads like a leaked credential. It was not: the token appears
**0** times. The check was right; the timeout was the bug. It is 180
seconds now.
