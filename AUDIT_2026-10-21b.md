## CRÍTICO

### H1 · `core.py:1035` — `consume_link_code` levanta `OperationalError: no such column: id` en **todas** las llamadas

**Archivo:linea exacta:** `core.py:1035-1051` (función `consume_link_code`).

**Descripción.** El esquema de `link_codes` (definido en `core.py:68-74`) usa
`code TEXT PRIMARY KEY` y **no tiene columna `id`**:

```python
CREATE TABLE IF NOT EXISTS link_codes(
  code TEXT PRIMARY KEY,
  user_id INTEGER NOT NULL,
  expires_at INTEGER NOT NULL,
  used_at INTEGER,
  created_at INTEGER
);
```

Pero el cuerpo de `consume_link_code` referencia `id` dos veces:

```python
# core.py:1043-1050
row = c.execute(
    "SELECT id, user_id, expires_at, used_at FROM link_codes WHERE code = ?",
    (code,),
).fetchone()
...
c.execute("UPDATE link_codes SET used_at = ? WHERE id = ?", (now, row["id"]))
```

El `SELECT id,...` falla con `sqlite3.OperationalError: no such column: id`
antes incluso de llegar al check `if not row: return None`. El UPDATE nunca se
ejecuta.

**Reproducir.**

1. En local (sin tocar nada del repo):

    ```python
    # /data/cache/scratch/test_consume_bug.py
    import os, sys, tempfile, traceback
    os.environ["UBOT_DB"] = tempfile.mktemp(suffix='.db')
    sys.path.insert(0, '/data/workspace/ubotpay')
    import unittest.mock
    with unittest.mock.patch.dict('sys.modules',
        {'web3': unittest.mock.MagicMock(), 'eth_account': unittest.mock.MagicMock()}):
        import core
        core.init()
        with core.conn() as c:
            c.execute(
                "INSERT INTO link_codes(code, user_id, expires_at, created_at) "
                "VALUES('7777777', 999, 9999999999, 0)")
        try:
            core.consume_link_code("7777777", 12345)
        except Exception as e:
            print(f"raised: {type(e).__name__}: {e}")
    ```
    Salida:
    ```
    consume_link_code raised: OperationalError
      message: no such column: id
    ```

2. En el VPS, contra el código real servido en `/opt/ubotpay/core.py`:

    ```bash
    API_KEY=$(grep ^UBOT_API_KEY= /opt/ubotpay/.env | cut -d= -f2 | tr -d '\r\n')
    curl -sS -o /tmp/r -w "status=%{http_code}\n" -X POST \

    ```

3. Diagnóstico del bug en el intérprete del VPS:

    ```bash
    /opt/ubotpay/venv/bin/python -c "

    print('init ok')
    core.consume_link_code('0000000', 1)
    "
    ```
    Salida:
    ```
    init ok
    consume_link_code raised: OperationalError: no such column: id
    ```

El bug se introdujo en `3967ee88 (Pedro Miranda 2026-10-20 00:05:35 +0000)`
durante "audit C1-C4 fixes" y nunca se detectó: los tests
(`test_wallet_ratelimit.py:128-185`) sólo inspeccionan el **texto** del fuente,
no ejecutan `consume_link_code` con un `INSERT` previo.

**Por qué el fix no es trivial.**

- `consume_link_code` no es la única referencia: `core.py` también expone
  `link_telegram_to_user` (línea 1054) que sigue un patrón paralelo (`UPDATE
  users SET telegram_id=? WHERE id=?` es válido porque `users.id` sí existe,
  pero la idea de "revisar siempre el esquema" no se aplicó aquí).
- Hay que decidir la semántica: si se cambia a `WHERE code = ?` falta resolver
  el TOCTOU — el código actual hace `SELECT` (comprueba `used_at IS NULL`),
  vuelve al caller, y después el caller hace el `UPDATE users`. Un atacante
  que reproduzca el mismo código antes del `UPDATE` puede llegar a estampar su
  `telegram_id`. Un fix correcto debe ser CAS atómico:
  `UPDATE link_codes SET used_at=? WHERE code=? AND used_at IS NULL` y
  verificar `cur.rowcount == 1`.
- El flujo entero (bot → `/auth/link-telegram/confirm` → `consume_link_code`
  → `UPDATE users SET telegram_id=?`) está roto *de extremo a extremo*: el
  usuario de Telegram que intenta vincular su cartera recibe "⚠️ That code
  didn't work" y nunca queda vinculado. El `link_telegram_to_user` JWT-based
  (línea 1054) sí compila pero no está siendo llamado por ninguna ruta (grep:
  un solo match, la propia definición).

**Estado en disco al cierre de la auditoría (2026-10-21, ~UTC 08:00).** En
`/data/workspace/ubotpay/` hay cambios sin commit en `api.py`, `bridge.py`,
`core.py`, `tg.py` (no míos — los aplicó otro subagente en paralelo). El diff
de `core.py` cambia precisamente las dos queries de `consume_link_code`:

```diff
-            "SELECT id, user_id, expires_at, used_at FROM link_codes WHERE code = ?",
+            "SELECT code, user_id, expires_at, used_at FROM link_codes WHERE code = ?",
 ...
-        c.execute("UPDATE link_codes SET used_at = ? WHERE id = ?", (now, row["id"]))
+        c.execute("UPDATE link_codes SET used_at = ? WHERE code = ?", (now, row["code"]))
```

Eso elimina el `OperationalError: no such column: id`. Verificado: tras
esos cambios, `consume_link_code('7777777', 1)` devuelve un usuario sin
explotar. **Pero el cambio deja intacto el TOCTOU** (el `SELECT ... WHERE
used_at IS NULL` y el `UPDATE` siguen siendo dos sentencias separadas), y en
`/opt/ubotpay/` (VPS) la versión servida por uvicorn **sigue siendo la vieja**:

```
$ ssh hvps 'grep "UPDATE link_codes SET used_at" /opt/ubotpay/core.py'
        c.execute("UPDATE link_codes SET used_at = ? WHERE id = ?", (now, row["id"]))
```

Por tanto, en **producción** H1 sigue activo: cada `POST
/auth/link-telegram/confirm` real es un 500.

**Severidad: CRÍTICO funcional — ALTO de seguridad.** No es un robo directo
de fondos (la ruta exige `x-api-key`), pero mientras el código esté roto, el
flujo de pairing Telegram↔wallet es 100% no funcional, y cualquier fix
superficial que sólo arregle la query sin cubrir el TOCTOU abre una puerta
de takeover de binding: dos requests concurrentes con el mismo código pueden
ganar ambos y el que estampe último gana. Verificado por simulación:

```python
# Resultado: 10/10 requests "succeed" con el UPDATE que sólo mira WHERE code=?
got user 42 - WINNER     (×10, todos pasan el check usado_a NULL y devuelven user 42)
```

## CRÍTICO (reabierto de la ronda 21 — el briefing de hoy no lo incluye)

### H2 · `chain.py:327-332` — un endpoint público envenena `_DEC` y rompe `send_usdc` para todo el proceso

**Archivo:linea exacta:** `chain.py:327-332` (`_balance_usdc`) y efecto sobre
`chain.decimals()` en líneas 36-40.

**Descripción.** `_DEC` (línea 33) es la caché global de `decimals()` y debe
ser un `int`. Pero `_balance_usdc` (línea 329) hace

```python
global _DEC
_DEC = w3l.eth.contract(Web3.to_checksum_address(c.usdc), abi=[...])
dec = _DEC.functions.decimals().call()
```

asignando un **objeto contrato** a `_DEC`. `decimals()` sólo recalcula si
`_DEC is None` (línea 38), así que **a partir de la primera llamada devuelve el
contrato** en lugar de `6`. `to_units()` (44) y `from_units()` (48) hacen
`10 ** decimals()`, lo que es:

```
TypeError: unsupported operand type(s) for ** or pow(): 'int' and 'Contract'
```

`send_usdc()`, `settle_authorization()` (cadena EIP-3009 de x402), y por tanto
toda ejecución de pago (`/approve`, `/turn confirm`, `/energy/order/{id}/settle`,
`x402/settle`) **deja de funcionar hasta el siguiente reinicio del proceso**.

Esto ya se documentó como **C-1 (CRÍTICO)** en `AUDIT_2026-10-21.md:19-67`,
pero el briefing de hoy no lo lista como cerrado y el código en `chain.py`
sigue intacto:

```
$ git log --oneline -- chain.py
6e12271 fix(security): rate-limits, otp retry, dead deps, requirement pins (round 21)
73d3e89 perf(db): turn on WAL, retry SQLITE_BUSY, set busy_timeout to 5s
71a2305 fix(energy): ...
```

`chain.py` no se ha tocado desde la ronda 21.

**Reproducir.**

1. Vector: cualquier persona en Internet puede pegar `GET /balance/<addr>?chain_id=8453`
   (8453 = Base; cualquier chain_id distinto de 43114/43113 es suficiente).
   El endpoint en `api.py:929-963` no requiere auth — sólo verifica que la
   dirección sea EVM y que la chain exista.

2. **Local** (mismo script de antes, importando `chain`):

    ```python
    # Después de inyectar chain._CHAIN_RUNTIME[8453] con mocks como arriba:
    print("Initial:", chain._DEC)
    chain._balance_usdc(FakeW3(), FakeChainObj(), fake_addr)
    print("After :", chain._DEC, type(chain._DEC).__name__)
    ```
    Salida:
    ```
    Initial: None
    After : <MagicMock id=...> MagicMock
    ```
    `chain.decimals()` ahora devuelve el objeto contrato, y:
    ```python
    chain.to_units(1.0)
    # TypeError: unsupported operand type(s) for ** or pow(): 'int' and 'FakeContract'
    ```

3. **En el VPS, con código real:**

    ```bash
    /opt/ubotpay/venv/bin/python <<'PY'
    import chain
    print('Before:', chain._DEC, 'decimals=', chain.decimals())
    try:
        chain.balance_at('0x713261F2151a759d9D935e6De2DB1d63A98176f6', chain_id=8453)
    except Exception as e:
        print('balance_at 8453:', type(e).__name__)
    print('After :', chain._DEC)
    print('decimals() now returns:', chain.decimals())
    try:
        chain.to_units(1.0)
    except Exception as e:
        print('to_units(1.0) raised:', type(e).__name__, ':', e)
    PY
    ```
    Salida exacta del proceso servido por el VPS:
    ```
    Before: None decimals= 6
    After : <web3._utils.datatypes.Contract object at 0x...>
    decimals() now returns: <web3._utils.datatypes.Contract object at 0x...>
    to_units(1.0) raised: TypeError: unsupported operand type(s) for ** or pow(): 'int' and 'Contract'
    ```

**Por qué el fix no es trivial.**

- Quien arregle tiene que decidir entre (a) cachear decimales por `chain_id`
  en `_CHAIN_RUNTIME` (preferible) o (b) variable local
  `dec_contract = w3l.eth.contract(...)` y `dec = dec_contract.functions.decimals().call()`,
  y luego `return Decimal(raw) / (10 ** dec)`. Cualquiera de los dos es
  trivial, pero **queda pendiente desde la ronda 21**.
- El estado envenenado del proceso es **invisible para el operador**: las
  excepciones se silencian en `core.mark`, `if not r["ok"]` y
  `except Exception` alrededor de `send_usdc`, así que el síntoma es "los
  pagos empiezan a fallar silenciosamente", no un crash.

**Severidad: CRÍTICO.** Trivial de explotar (un `curl` desde cualquier IP),
efecto total (rompe el camino de dinero para el proceso entero).
